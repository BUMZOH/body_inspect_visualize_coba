# 今後のダッシュボードアプリ開発方針

## 1. 目的

今後作成する工場向けダッシュボードアプリについて、技術選定と実装方針を整理する。

基本方針は **KISS（Keep It Simple, Stupid）** とする。

必要以上に構成を複雑化せず、実際の利用環境と要求に対して最も単純な構成を選択する。

------------------------------------------------------------------------

## 2. これまでの経緯

### 2.1 Flask / Webアプリへの移行

Flaskを利用するようになってから、HTML・CSS・JavaScriptを使用したWebアプリ形式のUIを積極的に検討してきた。

Web技術には以下の利点がある。

-   HTML / CSSによる自由度の高い画面設計
-   JavaScriptによるアニメーション
-   ブラウザ上での実行
-   レスポンシブデザイン
-   ネットワーク経由で複数端末から利用しやすい

さらに、pywebviewを利用することで、Web技術で作成したUIをデスクトップアプリとして利用する方法も採用してきた。

### 2.2 実際の利用条件の明確化

工場向けアプリを実際に開発していく中で、主な利用条件が明確になった。

-   Windows PC上で使用する
-   使用するPCは限定される
-   使用するユーザーも限定される
-   ブラウザからアクセスする必要がない
-   Full HD（1920×1080）など、表示環境を固定できる場合が多い
-   PLC、SQLite、CSV、JSONなどをPythonから直接扱う
-   データ処理の中心はPythonである
-   スマートフォン対応やレスポンシブ表示を必要としない場合が多い

この条件では、Web UIの利点の一部を使用していないことになる。

------------------------------------------------------------------------

## 3. 今後の基本方針

### 3.1 ダッシュボードUIはTkinterを第一候補とする

今後、工場PC上で動作するダッシュボードアプリについては、まず
**Tkinterで実現できるかを検討する**。

特別な理由がなければ、Tkinterを第一候補とする。

想定構成は以下とする。

``` text
PLC / SQLite / CSV / JSON
            │
            ▼
          Python
            │
            ▼
         Tkinter
            │
    ┌───────┼────────┐
    ▼       ▼        ▼
  Frame    Label    Canvas
```

Python内でデータ取得、処理、表示まで完結させる。

------------------------------------------------------------------------

## 4. Tkinterを採用する理由

### 4.1 Pythonだけで完結できる

pywebviewを利用する場合、一般的には以下のような構成になる。

``` text
Python
  │
  ▼
pywebview API
  │
  ▼
JavaScript
  │
  ▼
HTML / CSS
```

Python側で取得したデータを画面へ表示するために、PythonとJavaScriptの間でデータを受け渡す必要がある。

Tkinterでは、

``` text
Python
  │
  ▼
Tkinter
```

となり、Python内の値をそのままWidgetへ反映できる。

例：

``` python
data = get_data()
actual_label.configure(text=f"{data['actual']:,}")
```

表示のためだけに別言語へデータを渡す処理が不要になる。

### 4.2 PLC・SQLiteとの相性

工場向けアプリでは、以下の処理をPythonで行うことが多い。

-   PLC通信
-   SQLiteアクセス
-   CSV読み書き
-   JSON設定
-   HTTP通信
-   ログ記録
-   スレッド処理
-   定期更新

TkinterもPythonから直接操作できるため、これらの処理との接続が単純になる。

### 4.3 固定画面ではTkinterの弱点が小さい

今回の主な使用環境はFull HD（1920×1080）の固定PCである。

そのため、

-   スマートフォン対応
-   ブラウザサイズへの追従
-   複雑なレスポンシブレイアウト

などを考慮する必要がない。

固定レイアウトであれば、`Frame`、`Label`、`grid()`、`pack()`を組み合わせることで十分なUIを構築できる。

------------------------------------------------------------------------

## 5. Canvasの積極利用

Tkinterの標準Widgetだけでなく、ダッシュボードでは `Canvas`
を積極的に使用する。

Canvasを使用すると、以下を実装できる。

-   棒グラフ
-   進捗バー
-   DAY / NIGHT比率表示
-   境界線
-   目盛線
-   図形
-   簡単なアニメーション

今回の試作では、DAY /
NIGHTの比率バーについて、境界位置を一定時間揺らした後に実際の比率へ収束させるアニメーションを実装できた。

アニメーションには、

``` python
root.after(...)
```

を使用する。

単純なUIアニメーションのためにスレッドを追加する必要はない。

------------------------------------------------------------------------

## 6. 画像・簡易アニメーション

画面内のキャラクターなどについては、高度なアニメーション機構を導入せず、必要に応じて複数画像を一定間隔で切り替える。

例：

``` text
factory_bot_1.gif
        ↓
factory_bot_2.gif
        ↓
factory_bot_1.gif
        ↓
...
```

Tkinterの `PhotoImage` と `root.after()` で実装する。

ダッシュボードの補助的な演出については、この程度の単純な方式を基本とする。

------------------------------------------------------------------------

## 7. Flaskの役割

Flaskを使用しなくなるわけではない。

今後は主に **Web APIとしてPC間のデータ通信を担当させる**。

例：

``` text
設備PC（PC1）

PLC
 │
 ▼
Python
 │
 ├──── SQLite
 │
 └──── Flask Web API
              │
              │ HTTP
              ▼
          閲覧PC（PC2）
```

Flaskの主な役割は、

-   SQLiteから必要なデータを取得する
-   JSONとして返す
-   HTTP経由で別PCへデータを提供する

こととする。

UIを作るためではなく、**PC同士を接続するためのインターフェース**として利用する。

------------------------------------------------------------------------

## 8. 各技術の役割分担

今後の基本的な役割分担は以下とする。

  技術                      主な役割
  ------------------------- ----------------------------------
  Python                    アプリ全体の処理
  Tkinter                   PC上のGUI / ダッシュボード
  Canvas                    グラフ・図形・簡易アニメーション
  SQLite                    ローカルデータ保存
  Flask                     HTTP / Web API
  JSON                      設定・小規模データ
  CSV                       データ出力・交換
  HTML / CSS / JavaScript   Web UIが必要な場合のみ

それぞれの技術を、得意な用途に限定して使用する。

------------------------------------------------------------------------

## 9. pywebview / Web UIを採用する条件

Web技術を使用しないという方針ではない。

以下のような明確な理由がある場合には、pywebviewまたはWebアプリを検討する。

-   ブラウザから利用する必要がある
-   複数PCから同じ画面へアクセスする
-   スマートフォンやタブレットにも対応する
-   レスポンシブデザインが必要
-   HTML / CSSでなければ実現しにくい高度な表現が必要
-   JavaScriptライブラリを利用する明確なメリットがある
-   Webとして配布・運用すること自体にメリットがある

重要なのは、最初からWeb技術を前提にしないことである。

まず、

> Python + Tkinterだけで実現できない理由があるか

を確認する。

理由がなければTkinterを採用する。

------------------------------------------------------------------------

## 10. コード量について

今回の試作では、Web版はHTML・CSS・JavaScriptの3ファイルで構成され、Tkinter版はPythonのみで構成された。

単純な行数ではTkinter版が長くなったが、Tkinterコードは引数を複数行に分けるなど、可読性を優先した縦長の記述になっている。

一方、Web版では実際のアプリ化に伴い、

-   Python側API
-   JavaScript側API呼び出し
-   Python → JavaScriptのデータ変換
-   JavaScript側の画面更新

などが追加される可能性がある。

したがって、実際の設備アプリ全体では単純なUIファイルの行数だけで比較せず、

-   管理するファイル数
-   使用する言語数
-   データ受け渡し処理
-   修正時に確認する範囲
-   デバッグ対象となる層

まで含めて複雑さを評価する。

------------------------------------------------------------------------

## 11. 共通化・抽象化の方針

コードの重複を完全になくすことを目的にしない。

ダッシュボードでは、各画面・各タブの処理内容が具体的に読めることを重視する。

共通化する対象は、

-   明らかに同じ処理
-   修正内容も常に同じになる処理
-   関数化することで意味が明確になる処理

を基本とする。

一方、

-   名前を大量に引数で渡す必要がある
-   実際の処理内容が追いにくくなる
-   VS Code上でコードを追いにくくなる
-   具体的な画面とコードの対応関係が分かりにくくなる

ような共通化は避ける。

**DRYよりKISSを優先する場合がある。**

------------------------------------------------------------------------

## 12. 最新技術の採用方針

新しい技術やフレームワークは、「新しい」「高機能」「一般的にモダン」という理由だけでは採用しない。

採用判断では、

1.  現在の要求を解決する必要があるか
2.  既存の単純な方法では不足しているか
3.  導入によって複雑さ以上のメリットが得られるか

を確認する。

必要になった時点で複雑化する。

将来必要になるかもしれない機能のために、現在の構成を先に複雑化しない。

------------------------------------------------------------------------

## 13. 今後の標準構成

工場向けダッシュボードの基本形は、以下を第一候補とする。

``` text
dashboard_app/
│
├─ app.py
│
├─ daily_tab.py
├─ alarm_tab.py
├─ other_tab.py
│
├─ database/
│   └─ ...
│
├─ image/
│   ├─ ...
│   └─ ...
│
└─ config/
    └─ ...
```

`app.py` はアプリ全体の起動とタブ配置を担当する。

各タブは可能な限り独立させる。

``` text
app.py
 │
 ├── daily_tab.py
 ├── alarm_tab.py
 └── other_tab.py
```

各タブ内部では、その画面固有のWidget、データ取得、グラフ更新処理を具体的に記述する。

必要性が明確になった処理だけを共通関数へ移動する。

------------------------------------------------------------------------

## 14. 開発時の判断順序

新しいダッシュボードを作る場合は、概ね次の順序で判断する。

1.  使用環境は固定PCか
2.  ブラウザから利用する必要があるか
3.  Pythonでデータ処理を行うか
4.  TkinterのFrame / Label / CanvasでUIを実現できるか
5.  必要なアニメーションは `after()` で実現できるか
6.  PC間通信が必要ならFlask Web APIを追加する
7.  Web UIが必要な明確な理由がある場合のみHTML / CSS /
    JavaScriptを採用する

------------------------------------------------------------------------

## 15. 基本思想

今後のダッシュボード開発では、技術の多さや新しさではなく、**目的に対して必要十分であること**を優先する。

``` text
UIが必要
    ↓
Tkinterで十分か？
    │
    ├─ YES → Tkinter
    │
    └─ NO
        ↓
Web UIが必要な理由は明確か？
        │
        ├─ YES → pywebview / Web
        └─ NO  → 設計を再確認
```

最終的な基本方針は以下とする。

> **Python中心で構成し、PC用UIはTkinterを第一候補とする。\
> Flaskは必要に応じてWeb APIとして使用する。\
> Web UIは、Webであることに明確なメリットがある場合に採用する。\
> 必要になるまで構成を複雑化しない。**

これを今後の工場向けダッシュボードアプリ開発の基本方針とする。
